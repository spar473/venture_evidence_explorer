# Evidence and input contracts

These contracts govern representation and code verification. They do not certify
source truth, usefulness, investment attractiveness, or reviewer agreement.

`backend.ingestion.ImportDocument` strictly validates every object before opening
the destination database. Identifiers, names, aliases, text and nested arrays are
not coerced. Unsupported columns are refused with nested validation locations.
Cross references, evidence subjects, HTTPS sources, dates, calendar intervals,
award years and proposal isolation are checked. Imported annotations must remain
analyst proposals. A malformed import writes no records; immutable conflicts roll
back the whole data import. Migrations complete before the separate import
transaction, an intentional recovery boundary.

Input schema 1 accepts the historical seed without changing its bytes or hash.
Schema 2 adds optional `publication_date` to sources, `effective_date` and
`announcement_date` to observations, and `event_date_interval` to awards. Each is
an object with `precision`, `lower_bound`, `upper_bound`. `unknown` requires null
bounds; `day` requires equal valid calendar days; `month` and `year` require exact
calendar bounds (including leap years). No January 1 is substituted for a year.
Publication, retrieval, effective, announcement and event times remain distinct.
Day fields are still accepted for compatibility; conflicting day/interval values
are refused. Chronology rejects definitely impossible intervals: an earliest
possible publication after retrieval, or an earliest possible event after the
latest possible report day. Overlapping uncertain intervals remain uncertain;
a year-only event reported in October keeps its year precision. Exact days
still receive the original strict chronology checks.

The additive `003_historical_evidence.sql` migration preserves original tables,
seed and applied migration files. Canonical partial dates live in immutable
`evidence_dates`. The old source table has a NOT NULL publication string: schema
2 maps an unknown or partial publication to an empty legacy string, while API
hydration returns `published_at: null` and the canonical interval. Raw legacy
exports may show this as an empty cell. Every subsequent import stores the exact
input bytes in immutable `import_documents`, keyed by its original SHA-256 hash.
Historical import hashes are not recomputed or replaced. Original bytes for an
older import are recoverable only when its original file is supplied again;
bootstrap never manufactures them from database rows.

Observation relations append explicit correction/supersession links between
statements about the same venture and field, with a supplied reviewer, date and
rationale. Self links and cycles are refused during import. Statements remain
inspectable; new relations do not rewrite their wording. A relation is a supplied
record, not a reviewer judgment generated by this app. Contradictory statements
without a correction relation remain visible and may both supply wording; the
app does not decide which source is true.

`backend.evidence_policy` is shared by retrieval and raw profiles:

- Raw exploratory display retains all observations, conflicts, effective review
  status and correction links, including rejected/superseded statements.
- `exploration` retrieval explicitly allows source-checked but unreviewed
  publisher reports and reviewed accepted reports. It excludes rejected,
  needs-review and superseded statements. This policy keeps the original
  all-unreviewed sample usable without fabricated acceptance events.
- `accepted` matching requires an appended acceptance review event. An imported
  status label alone is insufficient. Latest review events determine current
  eligibility; analyst proposals and MCDA rubric ratings are excluded.
- A historical cutoff additionally requires `source_availability` containing a
  supplied availability day and evidence locator, at or before the cutoff.
  Publication labels and present-day retrieval do not establish past archive
  availability. Reviews and correction relations are evaluated as of the cutoff.
  No original seed source has such a witness, so historical selection abstains.
  Supplying a witness is a research responsibility; the application checks its
  representation, not the truth or accessibility of an archive.

# Feature research contract

Unknown features are valid and stay absent. The reusable
`backend.ingestion.ResearchFeatureAssertion` interface requires a venture, a
research dimension, a statement and observation IDs. A feature assertion must
identify its venture, a field, a statement, source observation IDs and whether it is source
wording or analyst interpretation. `ResearchFeatureAssertion` and `FEATURE_FIELDS` expose
the reusable interface. Existing observations already link source, locator, raw
wording and review state. Accepted structured matching may consume only eligible
reviewed source assertions; interpretations remain separate proposals. MCDA
rubric scores belong to MCDA Studio and are never inferred from these fields.

| Field | Research question |
|---|---|
| Identity | Which venture/project/legal identity does the evidence concern? |
| Problem / solution | What need and proposed intervention are actually reported? |
| Users / buyers | Who uses it, and who pays? Keep these distinct. |
| Technology / modality | What mechanism or product form is evidenced? |
| Business model | What supplied evidence describes revenue or contracting? |
| Validation | Which tests, population, comparator and limitations are reported? |
| Deployment | Where and when was actual use documented? |
| Route to market | Which customers, channels, regulatory or integration steps are evidenced? |
| Milestones | What happened, and with what event/announcement precision? |
| Financing | What amount, currency, qualifier, scope and time are explicitly reported? |
| UoA / community connections | Which overlapping institutional/community relationships have evidence? |

Schema 2 may attach `financial_value` or `event_value` to a sourced observation.
Financial values preserve raw amount, nullable ISO currency, qualifier, scope and
an explicit event interval. An ambiguous dollar sign does not imply NZD. Event
values preserve type, description and interval. These are records actually
supplied by an importer; the app never parses the seed into invented financial
values or generates a numeric score for each feature. No real accepted structured
feature corpus or relevance judgments were supplied in this implementation.

# Migration recovery

`migrate()` refuses an already active caller transaction. Transaction end uses explicit SQL COMMIT/ROLLBACK, including on Python 3.12+ connections configured with autocommit=True (where connection commit/rollback methods are no-ops). It explicitly begins
before each migration, and commits statements and checksum ledger together.
Failures roll back that migration's tables/views/triggers and ledger row. Earlier
completed migrations stay committed. Fix only the unapplied migration and retry;
an applied migration checksum mismatch requires investigation and a new additive
migration, never editing ledger checksums to suppress a mismatch. Back up the
SQLite database with SQLite's backup API before upgrading a research database.
